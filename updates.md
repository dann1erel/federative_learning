# Сопоставление требований с текущим проектом

Текущий проект закрывает только базовый эксперимент: CIFAR-10, IID-разбиение, FedAvg, accuracy и loss. До требований кафедры не хватает расширенных метрик, non-IID-сценариев, сравнения агрегаций и систематического сохранения результатов.

## 1. Что уже реализовано

- Датасет CIFAR-10.
- CNN для классификации на 10 классов.
- Федеративное обучение через Flower.
- IID-разбиение между клиентами через `IidPartitioner`.
- Агрегация FedAvg.
- Локальные train/validation-разбиения 80/20.
- Централизованная проверка глобальной модели на официальном test-наборе CIFAR-10.
- Метрики:
  - train loss;
  - validation loss и accuracy клиентов;
  - centralized loss и accuracy.
- Возможность сохранить финальную модель, но она выключена по умолчанию.

Основные места: `quickstart-pytorch/pytorchexample/task.py`, `quickstart-pytorch/pytorchexample/client_app.py`, `quickstart-pytorch/pytorchexample/server_app.py`, `quickstart-pytorch/pyproject.toml`.

## 2. Чего не хватает

### Обязательные метрики

Сейчас `test()` возвращает только loss и accuracy. Отсутствуют:

- precision;
- recall;
- F1-score;
- confusion matrix.

Для многоклассовой классификации одного числа недостаточно. Следует считать как минимум:

- macro precision, recall и F1 — каждый класс имеет одинаковый вес;
- weighted precision, recall и F1 — учитывается размер классов;
- per-class precision, recall и F1;
- confusion matrix размером `10 × 10`.

Основной показатель для сравнения алгоритмов при label skew — `macro F1`, поскольку accuracy и weighted F1 могут скрывать плохое качество на редких классах.

### Non-IID данные

В `task.py` явно используется `IidPartitioner`. Следовательно, все клиенты получают примерно одинаковое распределение классов.

Не реализованы:

- label skew;
- различное количество объектов у клиентов;
- feature skew;
- quantity skew;
- настройка силы неоднородности;
- сохранение распределения классов по клиентам.

### Разные алгоритмы агрегации

В `server_app.py` жёстко задан только `FedAvg`.

Нет сравнения хотя бы с:

- FedProx;
- FedAdam или другим FedOpt;
- SCAFFOLD — как более сложным этапом, если понадобится именно компенсация client drift.

Для первой законченной серии достаточно `FedAvg + FedProx + FedAdam`.

### Сохранение результатов

Результатов экспериментов в репозитории нет. Финальная модель сохраняется только при `save-model=true`, а сейчас установлено `false`.

Не сохраняются:

- метрики каждого раунда;
- параметры эксперимента;
- confusion matrix;
- распределение данных клиентов;
- время обучения;
- итоговая сводная таблица;
- графики;
- seed;
- лучший checkpoint.

Печать чисел Flower в консоль не является полноценным сохранением результатов.

### Воспроизводимость и экспериментальный протокол

Не хватает:

- глобального random seed для Python, NumPy и PyTorch;
- нескольких повторных запусков;
- среднего значения и стандартного отклонения;
- единой конфигурации экспериментов;
- фиксации количества клиентов и доли участвующих клиентов;
- описания аппаратного окружения;
- более реалистичного числа раундов.

Три раунда и одна локальная эпоха из текущей конфигурации подходят для проверки запуска, но недостаточны для содержательного сравнения алгоритмов.

### Документация проекта

README остался практически стандартным README шаблона Flower. В нём нет:

- постановки эксперимента;
- описания non-IID-разбиения;
- формул и способа усреднения метрик;
- команд воспроизведения;
- таблиц результатов;
- объяснения выбранных алгоритмов.

Корневой `main.py` содержит только `Hello, world!` и к экспериментам не относится.

## 3. Как развивать работу

### Шаг 1. Добавить корректный расчёт метрик

Изменить `test()` так, чтобы он накапливал все истинные метки и предсказания, а затем возвращал:

```text
loss
accuracy
precision_macro
recall_macro
f1_macro
precision_weighted
recall_weighted
f1_weighted
per_class_metrics
confusion_matrix
```

Перед проверкой модели обязательно вызывать `net.eval()`.

Для вычислений можно:

- добавить `scikit-learn`;
- либо вычислять confusion matrix и производные метрики средствами PyTorch.

Практичнее использовать `scikit-learn`, обязательно задав `zero_division=0`: при сильном non-IID некоторые классы могут полностью отсутствовать в предсказаниях клиента.

Confusion matrix удобнее сохранять как JSON/CSV и отдельно строить PNG. В Flower нельзя бездумно усреднять клиентские precision и F1: корректнее сначала суммировать клиентские confusion matrix, а затем вычислять глобальные метрики из общей матрицы. Централизованные метрики на общем test-наборе можно считать напрямую.

### Шаг 2. Реализовать параметризуемое разбиение

Добавить в конфигурацию:

```toml
dataset = "cifar10"
partitioner = "iid"
num-clients = 10
dirichlet-alpha = 0.5
seed = 42
```

Поддержать минимум два режима:

1. `iid` — контрольный baseline.
2. `dirichlet` — основной label-skew non-IID сценарий.

Для Dirichlet-разбиения сделать несколько уровней:

- `alpha = 10` — почти IID;
- `alpha = 1.0` — слабая неоднородность;
- `alpha = 0.5` — средняя;
- `alpha = 0.1` — сильная.

Чем меньше `alpha`, тем меньше классов обычно представлено у отдельного клиента.

Дополнительно полезен понятный искусственный сценарий `pathological label skew`, например по два класса на клиента. Он хорошо иллюстрируется, но Dirichlet лучше подходит для основной серии экспериментов.

Для каждого разбиения нужно сохранять таблицу:

```text
client_id, total_samples, class_0, class_1, ..., class_9
```

И строить heatmap распределения классов по клиентам. Без этого утверждение, что данные non-IID, экспериментально не подтверждено.

### Шаг 3. Не смешивать локальный и глобальный test

Рекомендуемая схема:

- исходный `train` CIFAR-10 распределяется между клиентами;
- внутри клиентской части выделяется локальный validation-набор;
- официальный `test` CIFAR-10 остаётся единым и не участвует в обучении;
- после каждого раунда глобальная модель оценивается на официальном test-наборе.

При non-IID желательно сохранять два вида результатов:

- глобальное качество на общем test-наборе;
- распределение локального качества клиентов: среднее, минимум, максимум и стандартное отклонение.

Это покажет ситуацию, когда средняя accuracy высокая, но отдельные клиенты получают плохую модель.

### Шаг 4. Добавить выбор стратегии

Вынести алгоритм в конфигурацию:

```toml
strategy = "fedavg"
proximal-mu = 0.01
server-learning-rate = 0.1
```

Реализовывать в таком порядке:

1. FedAvg — baseline.
2. FedProx — основное сравнение для non-IID.
3. FedAdam/FedYogi — адаптивная серверная оптимизация.
4. SCAFFOLD — только после стабильного экспериментального контура, поскольку он требует дополнительного клиентского и серверного состояния.

Важно: FedProx — не просто замена класса серверной стратегии. В локальный loss должен добавляться проксимальный штраф относительно полученной глобальной модели.

### Шаг 5. Организовать сохранение экспериментов

Для каждого запуска создавать отдельный каталог, например:

```text
results/
  cifar10/
    fedavg/
      dirichlet_alpha_0.1/
        seed_42/
          config.json
          round_metrics.csv
          client_metrics.csv
          class_distribution.csv
          confusion_matrix.csv
          confusion_matrix.png
          curves.png
          final_model.pt
```

`round_metrics.csv` должен содержать примерно такие столбцы:

```text
round, train_loss, test_loss, accuracy,
precision_macro, recall_macro, f1_macro,
f1_weighted, elapsed_seconds
```

Имя каталога или идентификатор запуска должны однозначно определять dataset, алгоритм, степень non-IID и seed.

### Шаг 6. Провести основную матрицу экспериментов

Минимальная убедительная серия:

| Фактор | Значения |
|---|---|
| Dataset | CIFAR-10 |
| Разбиение | IID, Dirichlet 1.0, 0.5, 0.1 |
| Алгоритм | FedAvg, FedProx, FedAdam |
| Seeds | 3 разных значения |
| Метрики | accuracy, loss, macro precision/recall/F1 |
| Дополнительно | confusion matrix, время, клиентский разброс |

Это 4 × 3 × 3 = 36 запусков. Если вычислительных ресурсов мало, сначала провести один seed для отладки, затем три seed только для финальных конфигураций.

Во всех сравнениях фиксировать одинаковые:

- модель;
- начальную инициализацию;
- клиентские разбиения;
- число раундов;
- число локальных эпох;
- learning rate;
- долю участвующих клиентов.

Иначе изменение качества нельзя уверенно связать с алгоритмом агрегации.

### Шаг 7. Расширить датасеты после CIFAR-10

Не стоит сразу добавлять много датасетов. Сначала довести полный pipeline на CIFAR-10.

Далее разумная последовательность:

1. MNIST или Fashion-MNIST — быстрые отладочные эксперименты.
2. CIFAR-10 — основной контролируемый benchmark.
3. CIFAR-100 — более сложный label-skew и оценка macro F1.
4. По возможности предметный датасет, связанный с темой диплома.

Для MNIST потребуется адаптировать первый слой CNN под один канал и размер изображения; для CIFAR-100 — последний слой под 100 классов. Лучше сделать модель параметризуемой через `num_channels` и `num_classes`.

## Ближайший практический приоритет

Работу стоит разделить на четыре последовательных этапа:

1. Добавить precision, recall, F1 и confusion matrix.
2. Сделать сохранение конфигурации, метрик, матриц и моделей.
3. Добавить IID/Dirichlet-разбиения и визуализацию распределений клиентов.
4. После проверки FedAvg добавить FedProx и FedAdam и запустить сравнительную матрицу.

После этих изменений проект уже будет соответствовать озвученным требованиям и станет основой для экспериментальной главы практики или диплома.
